# 文档审查（dsh-usage-stats）

本技能是「文档审查」的执行 SOP：审什么、怎么分工、怎么判、怎么改、改完怎么验。

**规则与归属不在本文件**：什么信息归哪份文档的权威是 `AGENTS.md` §10 与它的归属表，本文件只写流程与判定标准；执行时读那张表，不复述。

## 1. 边界

**审**：`AGENTS.md`、`README.md`、`CHANGELOG.md`、`docs/**`、`.agents/skills/*/SKILL.md`，以及 `src/**` 的注释。

**豁免（不改，最多在报告里提一句）**：

| 对象 | 限制 |
|---|---|
| `CHANGELOG.md` / `docs/releases/**` | 历史条目不重写（用户已经看过）；只查写法、错别字、口径 |
| `AGENTS.md` | 只改规则表述与归属表，不动现状事实 |
| `docs/STRUCTURE.md` | 生成物，只跑 `pnpm tree`，不手改 |
| `.agents/skills/release/SKILL.md` | 是发版流程权威，只报不改（改流程另起一轮） |
| `.agent-teams/`、`.local/`、`lib/`、`node_modules/` | 不审 |

## 2. 两种模式

- **审计模式（默认）**：只出问题清单，不动任何文件。用户看完清单再决定改哪些。
- **修复模式**：按 §7 的工单派单写入，同一文件同时只有一个写者。

用户没明说就按审计模式；说「直接改」才进修复模式，且 P0/P1 仍要先报。

## 3. 规模分档

| 规模 | 判定 | 编排 |
|---|---|---|
| 小 | ≤2 份文档且无跨文档搬迁 | 单 agent 顺序做，不上团队 |
| 中 | 3–6 份，改动都落在各自文件内 | 统筹 + 每文件一个 worker，一轮审完 |
| 大 | 全仓 / ≥7 份 / 有跨文档搬迁 | 走完整 P0–P4 |

技能本身不 spawn 任何 agent：由加载本技能的 agent（统筹）按 §4 派发。

### 团队能力检查（中 / 大档必做，动手前第一件事）

- **判定**：本会话可用工具里有没有派发子 agent 的能力（`subagent` / `subagent_fork` 一类）。有共享任务板（`team_task_*`）就一并用来表达写入范围与依赖，没有则退化为直接派单说明，不影响流程。
- **没有派发能力 = 本会话没有 Agent Teams，停止，不要用单 agent 硬跑**：7 万字文档 + 2 万行代码塞进一个上下文必然漂移，审出来的结论不可信，比不审更糟。
- 停止时把下面这段给用户，然后结束本轮：

```
本轮的文档审查需要 Agent Teams（多 agent 分工），当前会话没有启用。
请在 Agent Teams 设置里开启后重新发起，开启后说「继续审文档」即可接上。
顺带说明：只审 1–2 份文档不需要团队能力，可以直接说「只审 README 和 API.md」。
```

- 只有用户明确说「就单 agent 跑」才降级，且报告开头必须写明「降级模式：单 agent，未做跨文档比对，覆盖率不足」。

## 4. 阶段流程（大档）

### P0 建基准（并行 4 个）

机械校验 + 三片代码扫描，产出**一份**能力清单给所有审查者共用。

| 角色 | 范围 |
|---|---|
| 机械校验员 | 跑 `node .agents/skills/doc-review/scripts/check-docs.mjs`，FAIL 与 WARN 逐条记进清单 |
| host 片 | `src/host/**`、`src/types.ts`：账本与聚合、统计口径、Remote 方法签名、设置字段 |
| client 片 | `src/client/**`、`src/remote/**`：界面能力、设置项、浏览习惯存储、样式机制 |
| 交付片 | `tsdown.config.ts`、`.github/**`、`scripts/**`、`test/**`、根配置：构建产物、打包剪枝、CI 门禁、测试覆盖 |

产物写到 `.local/doc-review/facts.md`（不入库），每条一行：

```
能力/行为 | 用户可见效果 | 代码位置(file:line)
```

**这是唯一事实基准**：P1 里所有「文档说 A、代码是 B」都以它为准，不允许各 worker 自己再读代码下结论（那会得到 N 份不一致的口径）。

### P1 审查（并行，只读不改）

| 档 | 文件 | worker 数 |
|---|---|---|
| A 单份深审 | `AGENTS.md`、`README.md`、`docs/ARCHITECTURE.md`、`docs/API.md`、`docs/STYLE.md`、`docs/DETAIL.md`+`docs/DETAIL.en.md`（合一份，两份必须同步）、`.agents/skills/release/SKILL.md` | 7 |
| B 批量 | `CHANGELOG.md` + `docs/releases/**` | 1 |
| C 只校验 | `docs/STRUCTURE.md` | 0（交给 P0 机械项） |
| 注释 | `src/**` 头注首句与代码注释 | 1 |

每个 worker 的输入只有三样：**自己那份文档、`.local/doc-review/facts.md`、§5 的维度表**。不给全仓上下文。

- **读不设闸**：需要核对别处原文时直接读，读完把结论写进清单；不要向文档 owner 发请求（那会把漂移集中到瓶颈 agent，并把并行变成串行）。
- **写才设闸**：同一文件同一时刻只有一个写者，由统筹在 P3 派单。

### P2 仲裁（统筹做）

1. 归并全部清单、去重（同一问题被两个 worker 报出，合并为一条，保留更完整的证据）。
2. 按 `AGENTS.md` §10 的归属表判定「这条该去哪份文档」，跨文档搬迁一律在这里定落点。
3. 按 §6 分级，P0/P1 先报用户确认范围；P2 问用户是否要改；P3 只报不改。
4. 出工单：一条工单 = 一个文件的一段改动 + 期望结果。

仲裁必须是统筹自己做：它持有用户意图、归属表与分级标准，换成一个 subagent 只是把同样的规则再传一遍，还要多验一层。

### P3 修复（按文件派单）

- 一个文件同时只有一个写者；跨文件搬动拆成两条工单（源删 + 目标加），由目标文档的 owner 执行「加」。
- 改完跑 `pnpm tree`（涉及结构时）+ `check-docs.mjs`。发现新问题回到 P2，不要顺手扩大范围。

### P4 验收

机械项全绿 → 抽检 3 处（P0 事实错误是否真的改对）→ 报告给用户（会话里，不入库）。报告只写「改了什么、剩下什么」，不写过程记录（`AGENTS.md` §12）。

## 5. 审查维度

| # | 维度 | 查什么 | 判定方式 |
|---|---|---|---|
| 1 | 文档与代码不符 | 行为、字段、默认值、命令与实现不一致 | 人工（对 facts） |
| 2 | 内容放错文档 | 实现细节进用户面；用户语言进规则文件 | 人工（对归属表） |
| 3 | 重复表述 | 同一事实两处完整陈述 | 人工 + 机械 WARN |
| 4 | 啰嗦 | 一句话能讲清却写成 ≥3 句 | 人工 |
| 5 | 取证式细节 | 第 N 次尝试、耗时、提交 sha、命令输出原文 | 人工（判据见 §6） |
| 6 | 大段复制原话 | 改写就能讲清的长引用 | 人工（阈值见 §6） |
| 7 | 缺失（反向覆盖） | 代码有、文档没有：设置项、方法、门禁、能力 | 人工（facts 反查） |
| 8 | 口径不一致 | 同一名词两处定义不同；以代码为准 | 人工 |
| 9 | 过期示例 | 命令、配置片段、代码示例与当前实现不符 | 人工（可执行验证） |
| 10 | 失效指针 / 断链 | 指向已改名或已删的位置 | 机械 |
| 11 | 读者错位 | 该给维护者看的进了用户文档，反之亦然 | 人工 |
| 12 | 时态错位 | 计划/待定写成交付物；历史写成现在时 | 人工 |
| 13 | 术语不统一 | 同一概念多种叫法（见 `AGENTS.md` §1） | 机械词表 + 人工 |
| 14 | 文档自身结构 | 职责声明缺失、章节编号断、表格列数不齐 | 机械 + 人工 |

注释单独审：**注释的权威只有两件事**——文件职责（头注首句，即 `docs/STRUCTURE.md` 每行的数据源）与代码本身说不出的局部约束（`AGENTS.md` §10）。因此注释审查只问三句：头注首句与实际职责是否一致、这段注释是不是在复述代码、是不是在复制文档或写修复历史。

## 6. 分级与阈值

| 级别 | 例子 | 处置 |
|---|---|---|
| **P0 事实错误** | 文档说 X，代码是 Y | 必须改 |
| **P1 归属 / 重复** | 两处各写一遍凭据清单；实现细节进了 README | 必须改 |
| **P2 啰嗦 / 取证 / 原话** | 三段讲一个判断；「跑了 3 次第 2 次失败」 | 建议改，用户点头 |
| **P3 措辞偏好** | 断句、标题措辞、排版 | 只报不改 |

固定阈值（避免每次风格之争）：

- **取证式内容**：凡出现「第 N 次 / 耗时 / 提交 sha / 命令输出原文 / 逐条 diff」→ 判据是「读者做决策需要它吗」。需要（如「必须带 `--profile`」）保留，不需要就删。
- **大段复制原话**：连续引用 ≥3 行，或引用占该节 >30% → 改写为一句概括 + 保留可检索关键词（配置项名、用户会搜到的那句错误原文）。
- **啰嗦**：同一判断在相邻两句里重复出现 ≥2 次，或一个结论配了 ≥3 句铺垫。

## 7. 输出物

**问题清单**（P1 每个 worker 一份，直接回报统筹）：

| # | 位置 | 维度 | 证据 | 建议动作 | 目标文档 | 级别 |
|---|---|---|---|---|---|---|
| 1 | `README.md:102` | 3 | 与 `DETAIL.md:26` 各写一遍凭据别名 | 保留代码常量页，用户面留一行指针 | — | P1 |

**工单**（P2 产出，P3 执行）：

| # | 文件 | 段落（引首句） | 动作 | 期望结果 | 依赖 |
|---|---|---|---|---|---|
| 1 | `docs/API.md` | 「## 5. 偏好设置」 | 改写 | 字段表与 `src/host/settings.ts` 的 Config 一致 | — |

**验收报告**（P4，会话里给，不入库）：改动清单（文件 : 一句）→ 机械校验结果 → 剩余未处理项与原因。

## 8. 红线

- 无 Agent Teams 能力时不得静默降级成单 agent 硬跑（见 §3），也不能半路停下留一批改了一半的文件。
- 不重写历史（`CHANGELOG.md` / `docs/releases/**` 已发布条目）。
- 不手改生成物（`docs/STRUCTURE.md` 只跑 `pnpm tree`）。
- 不为「更规范」扩大范围：清单之外的改动一律回到 P2 重新过一遍分级。
- 找不到权威归属时先问用户，不要新建一份文档了事。
- 报告不入库（`AGENTS.md` §12）；中间产物只放 `.local/doc-review/`。
